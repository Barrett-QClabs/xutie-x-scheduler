x-unfollow rules (@barrett_tt)
- Untouchable: whitelist.txt only. Top-20 protection removed 2026-10-24.
- Unfollow plan (rules 2026-10-24):
  (1) ALL non-blue-V accounts the user follows — mutual or not, recent or not.
  (2) Blue-V accounts that do NOT follow back, EXCEPT the first 400 of the following list (most recent
      follows get time to follow back). Each blue-V target is re-checked (connection_status) right
      before the unfollow and skipped if it now follows back.
  Blue-V mutuals are NEVER unfollowed.
- Order: all non-blue-V first (oldest-followed first), then blue-V non-mutuals (oldest first). ~3 min gap (160-200s). Max 10/run (hourly), 100/day (Asia/Shanghai).
- Each unfollow logged to log.jsonl; never re-unfollow ids already in log, and never re-follow them
  (follow-back + keyword follow both skip every id in log.jsonl).

follow rules (follow-back + keyword follow share ONE daily budget)
- Combined follows (followback.jsonl + keywordfollow.jsonl, result ok, Asia/Shanghai day) <= 350/day
  (automation.config.json combinedFollowDailyCap). Both daemons check it inside a shared mutex
  (follow.mutex) right before every POST /2/users/:id/following.
- Shared 15-min window: <= 45 follow POSTs per 15 min across both daemons (X limit 50); 429 -> sleep to reset.
- Account-level 403 follow limit (or 2 consecutive 403s in keyword follow) -> follow-stop.json; both daemons
  stop following until the next Asia/Shanghai day.
- SHARED PACE (changed 2026-10-24): both daemons share ONE work/rest cycle.
  Work window: ≤ 10 successful follows TOTAL (follow-back + keyword mixed), ~75–105 s apart.
  Then a shared rest of 10–15 min (random) with ZERO follows of any kind, then repeat.
  State: follow-pace.json (workStartedAt / restUntil). Both daemons call waitForSharedWork.
- FOLLOW-BACK PRIORITY within each work window (swapped 2026-10-24 21:04 Asia/Taipei; before that keyword
  went first): follow-back of blue-V followers I don't follow yet takes slots first; keyword follow of NEW
  people fills the remaining slots in the SAME window (followbackYieldsSlot / follow-back window_yield/idle).
  Follow-back has no daily reserve limit beyond the combined 350 cap.
  Daily followbackReserve keeps room for follow-backs still waiting so keyword cannot use it up:
  reserve = min(blue-V follow-back targets still waiting, 10 per 30 min until Shanghai midnight);
  0 if follow-back is off / not running. Keyword only follows when combined + reserve < 350.
- Keyword pool: once per day keyword-candidates/YYYY-MM-DD.json, target 250 accounts from the FREE X plugin
  (search_posts_all + author expansions → plugin-pages/keyword/*.json → write-keyword-pool.mjs).
  Paid developer API is NOT used for search/user lookup. Categories: AI / 商业 / 两性 only.
  Query: "<kw> lang:zh is:verified -is:retweet". Filters: blue-V, followers ≤ 1000 inclusive (hard rule 2026-10-25, raised from 100),
  Chinese-zone, not protected, not already followed, not @barrett_tt, never unfollowed (log.jsonl) or
  followed before by any script. Daemon runs with NO_PAID_READS=1 (POST follow only; no paid pre-follow re-check).
- KEYWORD FOLLOW IS CHINESE-ZONE (中文区) ONLY (rule 2026-10-24 23:11 Asia/Taipei: "250个，必须是中文区的，
  英文区的不关注"); English-zone accounts are never keyword-followed. Follow-back is NOT affected.
  Search query is "<kw> lang:zh is:verified -is:retweet" for EVERY keyword (English ones too: AI, crypto,
  dating, sports, basketball, NBA, football, soccer → only Chinese tweets). Candidate rule (chineseZoneCheck):
    (1) matched tweet's X lang == "zh", AND
    (2) display name OR bio is Chinese: >= 2 CJK Unified Ideographs (U+4E00-9FFF, U+3400-4DBF, U+F900-FAFF)
        and Japanese kana < half the ideograph count (mentions/URLs ignored); OR, only if name AND bio contain
        no CJK ideographs and no kana at all, the matched tweet text has >= 4 ideographs (same kana rule).
    Japanese names/bios (kana-heavy or kana-only) are rejected with no tweet fallback.
  Same check runs again right before each follow with FRESH name/bio (together with the blue-V re-check).
  Pools built before the rule are refiltered (unchecked candidates are never followed):
  `node keywordfollow.mjs --refilter [--top-up]` (top-up = refill to 250 with lang:zh, within maxSearchPages).
- On/off toggles + keywords: automation.config.json (editable in 序帖 → 自动化 page).
- Never follow non-blue-V accounts (rule 2026-10-24): follow-back only targets blue-V followers;
  keyword follow only blue-V candidates from the plugin-built pool (NO_PAID_READS skips paid re-check;
  pool builder already filtered verified / followers / Chinese-zone / excluded).


read-saving (2026-10-25, user "能不能少读呢？" + approved widget t253s889)
- Shared cache.json: full following+followers refresh at most once per 7 days; otherwise maintain
  locally from followback.jsonl / keywordfollow.jsonl / log.jsonl deltas. Follow-back only pulls the
  newest followers pages until it hits a known follower id (headFollowers).
- GET /2/users/me cached in me-cache.json (7 days).
- Keyword pool: unused Chinese-zone candidates carry into the next day; search only tops the pool up
  to poolSize. Recent search returns tweets only (no user expansions); author ids already in
  keyword-rejected-authors.json / exclude are skipped BEFORE any GET /2/users. Unknown authors are
  looked up in batches of 100; rejects (tooManyFollowers etc.) are persisted so later pages/days
  do not re-bill them. Keywords with better historical add-rate are searched first.
- Pre-follow / pre-unfollow user re-checks use GET /2/users?ids=... in batches of 14 (USER_LOOKUP_BATCH),
  then act at the normal follow/unfollow pace. Covers blue-V + Chinese-zone (keyword) and
  connection_status follow-back (unfollow blue-V).
- 402 (credits depleted): daemons back off 5–10 min (not every 60s). 序帖 treats 402 as a pause, not a failed post.
- 序帖 timeline: one fresh read when a post is due (no 20-min watch polling). Stats: past UTC days cached
  permanently after the day ends; today TTL 60 min; panel auto-poll 30 min.
- Post interval: 30 min base + random jitter 0–300 s (queue_settings.random_min/max_seconds).
